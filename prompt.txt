2. Multi-tenancy should be a first-class primitive

Every business object should understand its tenant.

For example:

Platform
   │
   ├── Organization A
   │       ├── Users
   │       ├── Subscription
   │       ├── Projects
   │       └── Data
   │
   ├── Organization B
   │       ├── Users
   │       ├── Subscription
   │       ├── Projects
   │       └── Data
   │
   └── Organization C
           ├── Users
           ├── Subscription
           ├── Projects
           └── Data

The application shouldn’t repeatedly implement:

WHERE tenant_id = ?

Instead the framework handles tenant context.

For example:

const projects = await db.project.findMany();

The framework automatically applies:

currentTenantId

and prevents:

Tenant A → Tenant B data access

This becomes one of the framework’s most important security boundaries.

3. Pricing should be configuration, not application code

This is where I’d make the framework substantially better than many “starter SaaS” frameworks.

Define plans like:

plans:
  FREE:
    price: 0
    interval: month
    limits:
      users: 3
      projects: 2
      storage_gb: 1
      api_requests: 10000
    features:
      - basic_dashboard
      - api_access
  STARTER:
    price: 499
    currency: PHP
    interval: month
    limits:
      users: 10
      projects: 20
      storage_gb: 10
      api_requests: 100000
    features:
      - basic_dashboard
      - api_access
      - reports
      - email_support
  PRO:
    price: 1999
    currency: PHP
    interval: month
    limits:
      users: 50
      projects: unlimited
      storage_gb: 100
      api_requests: 1000000
    features:
      - advanced_reports

      - dedicated_support

Then your application simply asks:

if (entitlements.has("advanced_reports")) {
    ...
}

or:

if (usage.withinLimit("api_requests")) {
    ...
}

4. Separate Plans, Features and Entitlements

This is a very important distinction.

Don’t do:

if plan == PRO

Instead:

Plan
 ↓
Features
 ↓
Entitlements
 ↓
Permissions

For example:

PRO
 │
 ├── advanced_reports
 ├── api_access
 ├── automation
 └── integrations

A customer can then receive an entitlement independently of the plan.

Example:

FREE customer
+
temporary_trial("advanced_reports", 14 days)

Now your SaaS can easily implement:

* trials
* promotional features
* grandfathered customers
* beta features
* enterprise overrides
* add-ons
* reseller plans
* custom contracts

without changing application code.

6. Billing abstraction

Don’t hard-code Stripe.

Create:

BillingProvider
       │
       ├── Stripe
       ├── Xendit
       ├── PayMongo
       ├── Paddle
       └── Manual / Enterprise

Interface:

interface BillingProvider {
    createCustomer(...);
    createSubscription(...);
    cancelSubscription(...);
    changePlan(...);
    getInvoice(...);
    processWebhook(...);
}

Then your SaaS framework isn’t locked to one payment provider.

For a Philippine SaaS, I’d specifically design the abstraction so local providers can be plugged in.
